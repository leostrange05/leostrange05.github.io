# 面向对象设计与构造第一单元：表达式解析与运算

## 一、最终架构设计

### 1. 文件树

```text
src/
├── MainClass.java                — 程序入口，负责读取输入并驱动解析、计算与输出流程。
├── expr/                     ~ 表达式结构
│   ├── Expr.java                 — 表达式节点
│   ├── Term.java                 — 项节点
│   ├── Factor.java               — 因子抽象/接口
│   └── factor/               ~ 因子具体实现
│       ├── CallFunc.java         — 函数调用因子
│       ├── Derivative.java       — 求导因子
│       ├── ExpoFunc.java         — 指数函数因子
│       ├── ExprFactor.java       — 表达式因子
│       ├── PowerFunc.java        — 幂函数因子
│       ├── SelFactor.java        — 选择式因子
│       └── SignedInteger.java    — 常量因子/带符号整数
├── globl/                    ~ 函数定义
│   ├── DefFunc.java              — 非递推函数定义
│   └── RecFunc.java              — 递推函数定义
├── poly/                     ~ 多项式计算
│   ├── Mono.java                 — 单项式对象
│   ├── MonoKey.java              — 单项式键对象，用于同类项判等与合并索引
│   └── Poly.java                 — 多项式对象
└── syntax/                   ~ 词法语法
    ├── Lexer.java                — 词法分析器，将输入字符流切分为 token 序列
    └── Parser.java               — 语法分析器，将 token 序列构建为表达式语法结构
```

### 2. 类设计考虑

#### 1) `syntax` 词法语法

本模块负责将输入的字符串解析为语法树的各个组成部分。在 `Parser` 类中通过递归下降解析字符串，构建出表达式的层次结构。同时其还可以传入一个可选的“函数实参”成员，用于在函数调用时复用同一套解析逻辑，进行实参的代入与解析。

#### 2) `expr` 表达式结构

此模块表示了语法树的各个组成部分。核心类 `Expr`、`Term` 和 `Factor` 分别代表表达式、项和因子，形成了表达式的层次结构。`factor` 包下的具体实现类则对应不同类型的因子，根据不同因子的含义实现相应的计算逻辑。本模块**基本不实现算术运算**，仅负责表达式的结构化表示和基础的转化与化简，表达式的相乘括号展开也是通过调用 `Poly` 的运算方法来完成。

对于向多项式的转换，在 `Expr` 和 `Term` 类中均有 `solve()` 方法，负责将当前表达式/项转换为多项式对象。`Term` 类中的 `solve()` 方法将本项中包含的所有因子分类汇总，针对不同类型的因子进行不同的转化：常数和幂函数直接转换，其他类型的因子则进一步递归转换，例如表达式因子幂次的展开、选择式因子的选择求值等。

#### 3) `poly` 多项式计算

多项式 `Poly` 类最终采用一个 `HashMap<MonoKey, BigInteger>` 的容器来存储多项式中的单项式列表。HashMap 可以高效地实现**同类项的合并与查找**，且对于等价的多项式能够方便、快速地进行比较。加法、相反数、乘法等算术运算均有实现；同时编写了 `toString()` 方法，得到最终的输出结果。

考虑到运算功能需要尽量与 `expr` 模块分离，求导的运算在此模块中实现。相比于在 `expr` 模块中直接实现求导功能，在 `poly` 模块中实现求导可以更好地利用多项式的结构特性，简化求导的实现逻辑，并且使得求导的结果能够直接以多项式的形式进行后续的运算和输出。

#### 4) `globl` 函数定义

在本项目的实现中，函数定义的存储均采用字符串的形式。在解析函数调用时，直接将函数定义字符串传入 `Parser` 类中进行解析，**复用同一套解析逻辑**，实现函数实参的代入与解析。

#### 2) 基于度量数据的深入优缺点分析

##### 1. 内聚与耦合情况分析
*   **多态带来的高内聚与低复杂度（优点）**
    从度量数据可以看出，`expr.factor` 包下的所有具体因子类（如 `ExpoFunc`, `PowerFunc`, `SignedInteger` 等）的平均复杂度（OCavg）均在 `1.0` 左右，WMC 仅为 `2~3`。这说明这些类的**内聚程度极高**。我们通过抽象出 `Factor` 接口/父类，将不同的解析和转化逻辑分散到了各自的类中，完美符合了**单一职责原则(SRP)**。
*   **核心控制类的耦合不可避免（中性）**
    `syntax.Parser` 类的 WMC 达到了 `30`，`parseFactor()` 的圈复杂度达到 `15`。这是由于 `Parser` 作为构建抽象语法树（AST）的核心枢纽，必须与 `expr` 包下的所有节点类产生耦合。大量的 `if-else/switch` 用于判断 Token 类型是递归下降算法的固有特征。
*   **运算与表示的解耦（优点）**
    整个项目将结构（`expr`，包平均复杂度仅为 2.54）和运算（`poly`，包总复杂度最高，达到 92）进行了拆分。`expr` 层只做基础化简，而合并同类项、求导逻辑全部分配给了 `poly` 模块，实现了**逻辑解耦**。

##### 2. 缺点与自我点评
**自我点评：隐患与改进空间**
尽管整体架构切分合理，但从度量数据中也暴露出部分代码存在“代码异味（Code Smell）”，主要体现在以下两点：

1.  **输出逻辑过于臃肿（以 `Mono.toString()` 为例）**：
    `poly.Mono.toString()` 的圈复杂度达到了惊人的 **20**，认知复杂度达到了 **25**。在实现中，为了满足正确的输出格式（如省略系数1、省略指数1、项为0时不输出等），堆砌了大量的控制分支。
    *改进思路*：后续应当将“表达式的字符串格式化”逻辑单独抽离为一个 `Printer` 或 `Formatter` 类，或者将其分解为 `formatCoefficient()`, `formatVariable()` 等多个辅助方法，以降低单个方法的复杂度。
2.  **`Term.addFactor()` 违背开闭原则（OCP）**：
    该方法的圈复杂度达到 **10**。说明在向 `Term` 中添加因子时，可能使用了大量的 `instanceof` 或 `if-else` 来对因子类型进行特判。
    *改进思路*：如果未来再增加新的函数类型，此处必然需要修改代码。应当考虑让 `Factor` 提供更完善的接口（如类似访问者模式 `Visitor`，或者统一的 `mergeIntoTerm()` 方法），利用多态将判断逻辑下放到各个因子内部。




## 二、迭代过程中的设计体验

在第一次作业中，项目即形成了“`expr` 模块重解析、`poly` 模块重运算”的结构；在迭代过程中，项目的总体架构并未发生太大的变化，仅有新增功能的加入和微小的调整。此外还有一些细节上的设计优化和实现上的改进。

### 1. 迭代中的设计变化

#### 1) 多项式类的容器变化

在最初的设计中，我直接使用一个 `ArrayList<Mono>` 来存储多项式中的单项式列表，并专门定义了一个方法来合并同类项。然而在第二次作业时，由于等价比较实现不当，导致合并同类项的效率极低，非常容易超时。因此在第三次作业中，我将多项式类中的单项式列表改为一个 `HashMap<MonoKey, BigInteger>`，极大提升了效率。

#### 2) 记忆化与缓存意识的形成

第二次作业实现指数函数，在递归调用 `toString()` 方法时，我起初并未做任何缓存处理，导致嵌套多层指数函数时容易形成过大的递归树，最终导致超时。在 bug 修复阶段及第三次作业中，我对于每一个 `Poly` 对象都增加了 `stringCache` 成员，用于在第一次调用 `toString()` 方法后将结果缓存起来，后续再次调用时直接返回缓存结果，极大提升了效率。在后续的迭代中，对于递推函数的记忆化处理也是同样的思路。

---

### 2. 新增迭代任务的讨论

假设新增迭代任务：增加三角函数因子 `sin(因子)^k` 和 `cos(因子)^k`，则需要：

- 在 `expr/factor` 包下新增 `SinFunc` 和 `CosFunc` 两个类，作为三角函数因子对象
- 在 `Mono` 类中对单项式的最终结构进行调整：每一项增加两个 `HashMap<Poly, BigInteger>` 分别存储 `sin` 和 `cos` 的参数和幂次
- 在 `Term` 类的 `solve()` 方法中增加对于三角函数因子的处理逻辑，将其转化为对应的多项式成分进行后续的运算和输出

新增因子类型时，只需要考虑其在**最终 Poly 多项式中的表现形式**、其**自身拥有的成员参数**、以及**从表达式结构到多项式结构的转化逻辑**即可，其他部分的设计和实现基本不受影响，具有较好的扩展性。



## 三、作业中出现的 bug 分析

1. 第一次作业：暂未发现 bug
1. 第二次作业：
    - 未能正确处理函数定义式中 `x^+2`、`(x+1)^+2` 这类指数里有 '+' 的情况。
        - 原因：第一次作业为了图方便，在 `MainClass` 中预处理字符串时把所有的 `^+` 替换成了 `^`，但第二次迭代时忘记在自定义函数中也进行同样的预处理。
        - 解决：在第三次作业中，直接删去了 `MainClass` 中替换这一部分的逻辑，预处理只进行空白字符删除，把这类情况的处理留给 `Parser` 类中的语法分析逻辑来完成。
        - 总结：在开发周期长、迭代次数多的项目中，尽量**减少“一拍脑袋的特殊处理”**，需要保证逻辑的**一致性**和**复用性**，避免在将来的迭代中忘记对某些特殊处理进行维护和更新。
    - 合并同类项效率极低，导致超时。
        - 原因：在 `Poly` 类中使用了 `ArrayList<Mono>` 来存储单项式列表，并专门定义了一个方法来合并同类项。在实现 `equals()` 方法时，无脑选用题目规定的“多项式相等”的定义——两个多项式相减为 0。 由于每次判等都需要执行多项式剑法运算和合并同类项的操作，导致效率极低。
        - 解决：将多项式类中的单项式列表改为一个 `HashMap<MonoKey, BigInteger>`，极大提升了合并和判等效率。
        - 总结：在设计数据结构时，需要充分考虑其**性能特性**和**适用场景**，选择合适的容器来存储数据，以满足项目的性能需求。
    - 多层嵌套的 `toString()` 调用极慢
        - 原因：在 `ExpoFunc` 类中实现 `toString()` 方法时，直接递归调用 `toString()` 方法来获取指数函数参数的字符串表示，未考虑缓存处理，导致嵌套多层指数函数时形成过大的递归树，最终导致超时。
        - 解决：在 `Poly` 类中增加了 `stringCache` 成员，用于在第一次调用 `toString()` 方法后将结果缓存起来，后续再次调用时直接返回缓存结果，极大提升了效率。
        - 总结：在设计递归调用的算法时，需要考虑**递归树的规模**和**重复计算的情况**，适当引入缓存机制来避免不必要的重复计算，提高效率。
1. 第三次作业
    - 特定表达式展开时，结果的同类项合并异常
        - 原因：第三次作业中，由于直接使用了 HashMap 存储单项式列表，我将原本的合并同类项方法 `merge` 的功能改为“去除 HashMap 中系数为 0 的项”。但是，在多项式的加法、乘法等运算后没有及时调用 `merge` 方法，导致在某些特定表达式展开时，HashMap 中会存在大量系数为 0 的项，最终导致同类项合并异常。
        - 解决：在 `Poly` 类的加法、乘法等运算方法中，对返回值调用 `merge` 方法，确保 HashMap 中不包含系数为 0 的项。
        - 总结：设计时需尽量保证访问的对象都处于正确的状态，**避免出现“半成品”对象被其他方法访问**的情况。

### 1. Bug 与方法复杂度的相关性分析

1. **Bug 往往潜伏于低复杂度的“边缘”方法中**
   纵观这几次作业的 bug，大多出现在诸如 `Poly.equals()`（v(G)=3）、`Poly.add()`（v(G)=3）以及 `MainClass` 的预处理逻辑等**圈复杂度和代码规模低**的方法中。这说明本单元由于算法较基础，我遇到的 bug 很少是“控制流写错”导致的，反而大多缘于**容器选择不当**或**状态维护遗漏**（如运算后忘记调用 `merge()` 导致含系数 0 的废项）。这些可以说是架构设计与开发规范的失误。
2. **高复杂度方法的“幸存者偏差”**
   项目中圈复杂度最高的方法如 `Mono.toString()`（v(G)=20, LOC=62）和 `Parser.parseFactor()`（v(G)=15, LOC=54），反而没有出现功能性 bug。这是由于在编写这些分支庞杂的核心逻辑时，防备心理较重，重点关注了这些方法。但这并不值得骄傲，因为如此庞大的代码块已经几乎丧失了可维护性，一旦未来需要改动格式（如增加新的因子类型），极易引发连锁反应。
3. **递归调用的性能刺客**
   `Poly.toString()`（v(G)=10, LOC=39）复杂度偏高且承担着表达式递归结构化输出的职责。在此确实爆出了性能问题（未加缓存导致超时）。这说明当复杂逻辑伴生着深度递归时，性能开销的不可预见性会大大增加。

### 2. 降低方法复杂度的思考策略

反思这些拥有高圈复杂度的情况，可能在后续开发中采取如下方式来优化复杂的方法：

* **提取子方法**：
  针对 `Mono.toString()` 中为了满足诸如“系数1、-1省略”、“指数1省略”等堆砌的并排 `if-else`，可以将它们拆解成毫无耦合的辅助方法，例如 `formatCoefficient()`、`formatX()` 等。让主方法只负责按顺序调用它们进行字符串拼接（`StringBuilder`）。
* **用多态替换条件分支**：
  在 `Term.addFactor()`（v(G)=10）中，包含了大量的 `instanceof` 判断和转型，将不同因子塞入不同的容器。这是非常违背开闭原则的。实际上可以让 `Factor` 提供一个类似 `mergeInto(Term term)` 的方法，利用多态将具体的判断与存储归纳逻辑下放到各个因子具体类中去。
* **分离计算与展示的职责**：
  数学计算类（如 `Mono`，`Poly`）本身已经承担了大量的高复杂度运算（WMC高达 41），如果能将 `toString` 的任务剥离，专门编写一个独立的 `ASTPrinter` 或 `Formatter` 工具类处理格式化规范，能够大大降低 `Mono` 和 `Poly` 自身的逻辑厚度，降低耦合。

## 五、采取的优化策略

时间性能上的优化在上文基本均已提及，主要包括缓存与记忆化、以及合适容器的选择。下面主要说明输出长度上的优化。

* 如果多项式中有系数为正的项，保证输出结果的第一项为正系数项。这是第一次作业开始就有的优化。
* 检测指数函数 `exp((表达式))` 中的 “表达式” 是否为单个因子，如果是，可以直接输出为 `exp(因子)` 的形式。在此有必要介绍我的判断策略：
```text
    如果 多项式项数 > 1:
        return 非单个因子
    否则：
        引入单项式的“因子权重”
        因子权重 = [常系数 != 1] + [x 的指数 != 0]
                        + [y 的指数 != 0] + [exp 参数多项式 != 0]
        如果 因子权重 <= 1:
            return 单个因子
        否则:
            return 非单个因子
```
* 对于 exp 指数函数的参数多项式，可以通过将 `exp((a*k*x+b*k*x^2+...))` 转化为 `exp((a*x+b*x^2+...))^k` 的形式来减少输出长度。为了减少可能的时间开销，在枚举 `k` 的值时，我将搜索的范围进行了限制：令 `g = gcd(多项式项的系数集合)`，则 `k` 的搜索范围为 $k \in \{g/i | i \in \{2,3,...,9\}\}$。可以证明，在这个范围内的 `k` 一定包含了所有能够使输出长度减少的 `k`。

以上的优化保证输出结果正确，且对于代码的简洁性没有太大的影响。我没有采用过于复杂的将一个 exp 指数函数分组拆分后提取公因数的优化，虽然这种优化在某些特定的表达式下能够进一步减少输出长度，但其实现较为复杂，且极易增加时间开销。

## 七、本次作业心得体会

1. **面向对象的设计习惯仍需培养**
   虽然仿照第一次实验中的架构，我很自然地形成了递归下降的解析器和分层的表达式结构，但是在某些细节上仍然存在“面向过程”的痕迹，例如在 `Term.addFactor()` 中大量的 `instanceof` 判断和转型，导致了代码的臃肿和违背开闭原则。在这方面，我需要继续加强面向对象设计的意识，学会利用多态和抽象来减少条件分支，提高代码的可维护性和扩展性。
2. **警惕“技术债”与容器选择的重要性**
   为了图快而在初期采用的偷懒方式（如暴力替换字符串、使用 `ArrayList` 遍历合并同类项）都在后续变成了难解的 BUG 甚至是 TLE 性能瓶颈。直到将多项式存储重构为 `HashMap`，并加入 `stringCache` 缓存机制，才彻底解决。这让我明白，写代码时不能只顾眼前，良好的数据结构和前瞻性设计远比临时工式的 trick 可靠。
3. **直面“代码异味”，敬畏代码质量**
   OO 度量分析像一面镜子，照出了我那些塞满 `if-else` 的臃肿代码（如巨长的 `toString`）。尽管它们暂时没有报错，但我深刻感受到了这些“高复杂度炸弹”带来的维护压力。未来我还需要学习更多的架构手段，去化解这些臃肿的方法。
4. **与大模型（AI）共驾的边界**
   在编写评测脚本和处理局部疑难细节上，大模型表现出了惊人的效率；但在核心架构搭建和复杂的化简算法上，人脑的系统级规划仍不可替代。AI 是极佳的副驾驶，但开发者必须亲自握稳方向盘。

面向对象不仅是语法的堆砌，更是一种**管理复杂度的艺术**，期待在下一单元中能写出更加优雅的代码。

## 八、未来方向

第一单元的内容安排已经较为合理，难度也适中。三次作业的工作量还算均衡，第二次作业的迭代可能略微有些繁重。

在课程的指导上，或许可以更多地结合具体任务的实现给出一些设计模式的建议，从而引导我们优化代码结构。
